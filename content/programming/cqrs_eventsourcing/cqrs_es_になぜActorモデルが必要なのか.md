# CQRS / ES における Actor モデルの必要性とアーキテクチャ

## 1. 前提知識と背景

### 基本アーキテクチャ概念
- **Shared Nothing Architecture (SN):**
    - 分散コンピューティングにおいて、各ノードがネットワーク以外でリソースを共有しない構成。
    - 各ノードは独立・自律しており、単一競合箇所が存在しない状態を指します。

### CQRS / ES の基本実装
- **構造:**
    - ドメインモデルは「コマンド側」のみに存在し、クエリ側には登場しません。
    - コマンドを受け付けることでドメインモデルが更新されます。
- **データフロー:**
    - 格納されたイベントを Subscription するコンポーネント（Read Model Updater や EventForwarder）が動作します。
    - これらが RDS を更新したり、WebSocket でクライアントへ配信したりします。

> **Note: Actor モデルを使わないアプローチ**
> - **[j5ik2o/event-store-adapter](https://github.com/j5ik2o/event-store-adapter):**
    >   - DynamoDB を CQRS のイベントストアとして利用するためのライブラリ。
>   - **開発動機:** 誰もが Actor Model を扱えるわけではないため、通常のオブジェクトモデルでも CQRS / ES を可能にするために開発されました。

---

## 2. 課題：分散環境における並行性と整合性

Write API Server をスケールさせる際、**「複数のユーザが同時にコマンドを送信する場合」**に以下の問題が発生します。

### 順序性と整合性の担保
- **問題点:**
    - 単一のアグリゲートに対し、「Command1 -> Command2」の順で送信しても、処理順が「Command2 -> Command1」になるとデータの整合性が壊れます。
    - **ES (Event Sourcing) 特有の事情:**
        - アグリゲートの状態を復元（リプレイ）する際、イベントの順序が命です。
        - 例: `add` -> `remove` のつもりが `remove` -> `add` で格納されると、リプレイ時にエラーや不正な状態になります。

### 従来の解決策（楽観的ロック）とその弊害
順序を守るために「楽観的ロック」を採用した場合、以下の副作用が生じます。

- **UX の低下と実装コスト:**
    - 競合に負けたユーザにはエラーが返されます。
    - クライアント側でリトライ処理が必要になり、実装負担が増加し、UX が低下します。
- **パフォーマンス:**
    - 独立して操作できるものに対しても、常にロックを獲得する必要があります。

---

## 3. 解決策：Actor モデルの導入

Actor モデル（特に Persistent Actor）を導入することで、ロックフリーかつ整合性の取れた処理が可能になります。

### Actor の定義と特性
- **基本単位:** 計算の基本単位であり、状態・振る舞い・メールボックスを持ちます。
- **通信:** メッセージパッシングという唯一の手段で通信します。
- **処理:** **一度に1つのメッセージのみ**を処理します（シングルスレッド的な挙動）。
- **機能:** メッセージ送信、新規 Actor 作成、自身の状態変更が可能です。

### なぜ並行性が単純化されるのか

| 特徴 | 従来（共有メモリ + ロック） | Actor モデル |
| :--- | :--- | :--- |
| **排他制御** | ロックが必要 | **ロックフリー** |
| **構成** | 複数スレッドが共有データを操作 | **1 Aggregate = 1 Actor** (Entity Actor) |
| **処理フロー** | 競合時にエラーや待機が発生 | メールボックスにキューイングされ**逐次処理**される |
| **データ源** | DB等を正とする | Actor が**信頼できる唯一の情報源 (SSoT)** となる |

### CQRS/ES における具体的なメリット
- **Single Write の実現:**
    - Persistent Actor は「1 アグリゲートに対して 1 つ」割り振られ、全ノードの中で唯一の存在となります。
    - ID: 101 に対する操作は必ず特定の Actor インスタンス（ID: 101担当）に集約されます。
- **位置透過性と回復性:**
    - Journal (永続化層) から状態を復元できるため、Actor はどの Node で起動しても問題ありません。

## 4. Actor Cluster の構成と進化

Actor を分散配置（クラスタリング）する際の仕組みと、それに伴う新たな課題、そして解決策です。

### 基本的な Cluster 構成要素
1. **Entity Actor:**
    - 実際のアグリゲート処理を行う Actor。
2. **Shard:**
    - 複数の Entity Actor を束ねて管理する単位。
3. **Shard Coordinator:**
    - クラスター内に1つ立ち上がり、DNS のような役割を果たします。
    - 各 Shard の担当ノードを管理し、負荷分散を行います。

### 課題：Akka / Pekko の弱点
- **SPOF (Single Point of Failure):**
    - Shard Coordinator がクラスター内に1つしか存在しないため、単一障害点になります。
    - Coordinator の再配置や再起動時にレイテンシーが悪化する可能性があります。

### 進化系：Virtual Actors と次世代ライブラリ
SPOF を排除し、可用性を高めるためのアプローチです。

- **[ProtoActor Go](https://github.com/asynkron/protoactor-go):**
    - Shard Coordinator の役割を Node 上ではなく外部（外出し）に持たせるアーキテクチャ。
    - 再起動時のレイテンシー悪化を防ぎます。
- **Virtual Actors (分散協調):**
    - **特徴:**
        - ハッシュ計算を用いた分散協調により、**SPOF を排除**しています。
        - ローリングアップデートをどのノードから始めても問題ありません。
    - **参考資料:** [Zenn: Virtual Actors について](https://zenn.dev/j5ik2o/scraps/0edd6d7a23667b)
- **Rust による実装:**
    - **[j5ik2o/fraktor-rs](https://github.com/j5ik2o/fraktor-rs):** Rust 言語による実装例。
