# Why CQRS?

データのCRUDが中心のアーキテクチャではドメイン駆動設計が不可能である
ユビキタス言語の動詞が CRUD に収束することはあまりない

CRUD 思考の UI にはユーザの意図が組み込まれていない
概念モデルを深く理解しないと使えない
システムがユーザの意図を薄なうと役立つレポーティング情報を提供できない

# CQRS
CQRS はオブジェクトをこメンドとクエリに分離する単純なアーキテクチャパターンだが、その恩恵を受けるにはユーザの意図を汲み取って体験に気を配る必要がある

## Command

言語的な意味から考えるとシステウが命令を拒否できることを示している
ユーザの意図を煮詰めると同時に拒否される理由をよく考える
拒否をただのエラーとして扱わずにユーザ体験として設計に練り込んでおく

## Event

言語的な意味から考えると事実は取り消せないことを示している
すでに起きたことを拒否するのは不自然であり、コマンドとは意味的な対照性がある

## Command & Event

言語的な意味に注目し、ドメインモデルとユビキタス言語の探索に使う

技術的にはどちらも単純な構造体という点で同じであるが命名方法に違いがある。

## Event Storming

イベントストーミングをデザインの手法として活用する(設計ではなく)
異なるバックグラウンドを持つ人の勧化を発散させ、カラーパズルと対話を通して合意させる
まずは問題を深く探ってそれから解決へ収束させていく点でデザイン思考によく似ている

## Aggregate

普遍条件を矯正する範囲、つまり一っ完成と同時実効性の単位
同一集約に対する同時実行で不変条件が破られないようにする必要がある
処理待ちや失敗の増加によるユーザ体験の悪化に注意する

## Policy

集約の普遍条件ではない比較的緩やかなビジネス上の意思決定
イベント発生や時間経過で起動するリアクティブロジック

例)「在庫で、一旦在庫のマイナスを許容して処理を継続する」

## Aggregate & Polocy

制約を守りながら柔軟でノンブロッキングなインタラクションを考える
DB ロックすればいいと技術主導で考えないように売る

# 現実

上記は教科書の上での話だが、現実ではどうだろうか。

## 例) サブスク登録している顧客にだけコミュニティ(アーティストや作品)の限定投稿を見せたい

下記のような症状が起きた
- 限定投稿を観れるか判定するために毎回決済状態をチェックしないといけずコードが煩雑
- UI 上で自分がサブスクリプションしているコミュニティをどう表現すればいいか不明瞭

そこで起きているコトに注目した
チェックインする時「サブスクという支払い契約」を都度確認してもらっているわけではなく、課金を済ませたら会員証を受け取っている

なので、「会員証を受け取る」というイベントを発火するようにした

ドメインモデルの変化がユーザ体験を変化させる
会員証リッチなカードデザインにして見せるコトで所有官や貴族感を高める体験に。期間限定のカードデザインなど新しい価値を考えるためのきっかけになる。

# ドメインに踏み込んで解決策を総図する
ドメインエキスパートはサブスクという安定収益を第一に考えていた。ドメインエキスパートは個別に特化した知識を持っているが全体最適の解決策を持っているわけではない。
技術力と想像力で自分たちなりのシェアパイを発見する

# CQRS を使わないとき

CQRS は未開拓の領域を扱う時には採用しない。ただしコマンド・イベント・集約・ポリシーは実装する。

CQRS+ES はパフォーマンスとスケーラビリティに寄与する
コマンドとクエリを個別に最適化できるのでハイトラヒックかつ競合が起きやすい領域に向いている
イベントバージョニングや集約境界変更の頻度が高い不安定な領域では変更コストを回収するのが難しい

## 結果整合のクエリはユーザ体験に直接的な影響がある

最新ではないデータを見ている可能性をユーザ体験に織り込んでおく設計コストの前払いが必要
明らかにスケーラビリティが必要ならリードレプリカを後からつぎはぎで入れるよりは良いかもしれない。

# では CRQS / ES  を使わないならどうやる？

## Immutable Data Model

RDS でイベントとリソースを区別しながらテーブル設計する
イベントの疑念的恩恵を受けつつも結果整合のクエリが必須ではなくなる
必要な table join が増えたりインピーダンスミスマッチが激しくなる可能性がある

## CRUD vs CQRS
CRUD をユビキタス言語にしている部分の CQRS 実装は無駄。(Update Edit Add のみのような。)
コマンドに意図がなく集約で矯正する普遍条件がなくお年とは実質集約のスナップショットに。

# まとめ
まずはドメインに向き合ってそれから CQRS で実装する
ドメインモデルを洗練する方が、事業に長く大きく貢献してくれるそう。
