# Message Dispatcher

## パターンの概要

Message Dispatcher（メッセージディスパッチャー）は、チャネルからメッセージを取得し、処理を担当するパフォーマー（実行者）に配布するパターンです。ディスパッチャーは、複数のコンシューマーが単一のメッセージチャネル上で協調して動作するための調整役として機能します。このパターンにより、メッセージ処理の並行性を効率的に管理し、ワークロードを適切に分散させることができます。

## EIPにおけるMessage Dispatcher

### 解決すべき問題

アプリケーションがメッセージングを使用しており、**単一のメッセージチャネル上で複数のコンシューマーが協調して動作する必要がある**という状況があります。各コンシューマーがそれぞれ独立してチャネルからメッセージを取得するのではなく、中央集権的にメッセージの配布を制御したい場合があります。

例えば、以下のようなシナリオを考えてみましょう。

**ワークロードの均等化**では、複数のワーカーがいる場合、一部のワーカーに作業が集中し、他のワーカーがアイドル状態になることがあります。作業を均等に分散させるために、各ワーカーの現在の負荷を考慮してメッセージを配布したい場合があります。

**専門化されたワーカーへの振り分け**では、異なるタイプのメッセージに対して、それぞれ専門のワーカーが存在する場合があります。メッセージの内容を確認し、適切な専門ワーカーにメッセージを振り分けたい場合があります。

**リソースの効率的な利用**では、ワーカーのプールを管理し、必要に応じてワーカーを生成または選択することで、リソースを効率的に利用したい場合があります。

### 解決策

チャネル上に**Message Dispatcher**を作成し、チャネルからメッセージを取得してパフォーマーに配布します。

Message Dispatcherは二つの主要な構成要素からなります。

**Dispatcher（ディスパッチャー）**は、チャネルからメッセージを取得し、各メッセージを適切なパフォーマーに配布するコンポーネントです。ディスパッチャーは、どのパフォーマーにメッセージを送るかを決定する責任を持ちます。

**Performer（パフォーマー）**は、ディスパッチャーから受け取ったメッセージを実際に処理するコンポーネントです。各パフォーマーは、割り当てられた作業を実行し、必要に応じて結果を返します。

### Message Dispatcherの動作特性

**パフォーマーの選択**として、ディスパッチャーがメッセージを受信すると、そのメッセージを処理するパフォーマーを選択します。パフォーマーは新たに生成されることもあれば、利用可能なプールから選択されることもあります。

**並行処理の実現**として、各パフォーマーは独自のスレッドまたは実行コンテキストで動作できます。これにより、複数のメッセージを同時に処理する並行処理が可能になります。

**メッセージプロパティに基づく配布**として、ディスパッチャーはメッセージのプロパティ（タイプ、優先度、内容など）を確認し、特定のパフォーマーとメッセージをマッチングすることができます。これにより、専門化されたワーカーへの効率的な振り分けが可能になります。

### Content-Based Routerとの違い

Message DispatcherはContent-Based Routerと似ているように見えますが、重要な違いがあります。

**ワークロードへの関心**として、Content-Based Routerはメッセージの内容のみに基づいてルーティング先を決定し、各ルーティング先の現在のワークロードには関心を持ちません。一方、Message Dispatcherはパフォーマーのワークロードを主な関心事とし、負荷が最も低いパフォーマーにメッセージを配布しようとします。

**配布先のスコープ**として、Content-Based Routerはプロセス境界を越えて分散した複数のシステムにメッセージをルーティングすることが多いです。Message Dispatcherは、同一プロセス内のワークタスクをディスパッチすることを想定した設計になっています。

**配布基準の違い**として、Content-Based Routerはメッセージの内容のみを配布基準とします。Message Dispatcherは、メッセージの内容に加えて、ワーカーの既存ワークロードも考慮して配布先を決定します。

## アクターモデルにおけるMessage Dispatcher

### アクターシステムにおけるDispatcher

アクターモデルでは、Message Dispatcherパターンは複数の形で実現されます。Akkaは、様々なMessage Dispatcherをサポートしており、また同様の機能を持つルーターも提供しています。

### 標準ディスパッチャーの種類

Akkaは、異なる特性を持つ複数の標準ディスパッチャーを提供しています。

**デフォルトDispatcher**は、Akkaの標準的なディスパッチャーです。アクターのセットをスレッドプールに関連付けます。各アクターは、必要に応じて異なるディスパッチャーを選択して使用することができます。ほとんどのユースケースでは、このデフォルトディスパッチャーが適切です。

**PinnedDispatcher**は、各アクターに専用のスレッドを割り当てるディスパッチャーです。このディスパッチャーを使用するアクターは、実質的に1つのアクターのみが割り当てられた専用スレッドプールを持つことになります。ブロッキング操作を行うアクターや、他のアクターと実行を共有したくないアクターに適しています。

**BalancingDispatcher**は、最もタスクが少ないアクターにメッセージを分散しようとするディスパッチャーです。このディスパッチャーによって管理されるすべてのアクターは同じメールボックスを共有し、すべて同じ型である必要があります。ただし、このディスパッチャーは現在非推奨となっており、代わりにルーターの使用が推奨されています。

### ルーターによるMessage Dispatcherの実現

BalancingDispatcherの代替として、Akkaは優れたMessage Dispatcherとして機能するルーターを提供しています。

**RoundRobinRouter**は、設定された数のroutee（ルーティング対象アクター）を持ち、ラウンドロビン順序で各routeeにメッセージを送信します。このルーターはrouteeのワークロードを判断しないため、各メッセージの処理時間が均一な場合に最適です。

**SmallestMailboxRouter**は、自身のメールボックスに最も少ないメッセージ数を持つ、サスペンドされていないrouteeにメッセージを送信しようとします。これはBalancingDispatcherの最良の代替となります。各routeeのメールボックスサイズを確認し、負荷が最も低いrouteeを選択することで、ワークロードの均等化を実現します。

### ボランティアリングスタイル

標準のディスパッチャーやルーターを使用する代わりに、**ボランティアリングスタイル**のアプローチも検討できます。このスタイルでは、各ワーカーアクターが作業を必要とするときに、作業プロバイダー（ディストリビューター）に自ら通知します。

**ボランティアリングスタイルの動作**として、ワーカーは現在の作業を完了すると、ディストリビューターに「作業が必要です」というメッセージを送信します。ディストリビューターは、利用可能な作業があれば、要求したワーカーに作業を割り当てます。

**このアプローチの利点**として、ワーカーが自身の処理能力に応じて作業を要求するため、自然なバックプレッシャーが実現されます。また、Akka内部の詳細な知識を必要とせず、シンプルなメッセージパッシングで実装できます。

**考慮事項**として、ワーカーがディストリビューターについて知っている必要があり、ワーカーからディストリビューターへの追加のメッセージ送信が必要になります。しかし、この追加のオーバーヘッドは、標準ツールが内部で行うチェックのオーバーヘッドと比較して、多くの場合許容範囲内です。

### リモートアクターに関する考慮事項

SmallestMailboxRouterをリモートアクターと共に使用する場合、重要な制約があります。ルーターはリモートアクターのメールボックスサイズを直接確認できないため、リモートアクターへのルーティングは「最後の選択肢」として扱われます。

**実践的なアプローチ**として、分散システムでMessage Dispatcherを効果的に使用するには、各ノードにローカルルーターを配置し、ノード間の負荷分散は別の仕組み（クラスターシャーディングなど）で行うことが考えられます。

## Message Dispatcherの設計考慮事項

### パフォーマーの管理

**プールサイズの決定**として、パフォーマープールのサイズは、処理能力とリソース消費のバランスを考慮して決定します。プールが小さすぎるとスループットが制限され、大きすぎるとリソースが無駄になります。

**動的なリサイズ**として、ワークロードに応じてパフォーマープールのサイズを動的に調整することで、リソースの効率的な利用が可能になります。負荷が高いときはパフォーマーを追加し、低いときは削減します。

### 障害処理

**パフォーマーの障害**として、パフォーマーが障害を起こした場合、ディスパッチャーはその障害を検出し、処理中だったメッセージを他のパフォーマーに再配布するか、適切なエラーハンドリングを行う必要があります。

**監視と復旧**として、ディスパッチャーは各パフォーマーの状態を監視し、障害が発生したパフォーマーを復旧または置換する責任を持つことがあります。

## 関連パターン

- **[[programming/reactive_messaging_pattern/chapter7/simple-routers/content_based_router|Content-Based Router]]** - メッセージの内容のみに基づいてルーティング先を決定するパターンです。ワークロードには関心を持ちません。Message Dispatcherは、Content-Based Routerの機能に加えて、パフォーマーのワークロードも考慮します。

- **[[programming/reactive_messaging_pattern/chapter9/consumers/competing_consumers|Competing Consumers]]** - Message Dispatcherによってメッセージを配布される複数のコンシューマーです。ディスパッチャーが配布先を決定する点で、純粋なCompeting Consumersとは異なります。

- **[[programming/reactive_messaging_pattern/chapter9/consumers/polling_consumer|Polling Consumer]]** - ボランティアリングスタイルのMessage Dispatcherは、Polling Consumerパターンと組み合わせて使用できます。ワーカーが作業を「要求」する形式です。

- **[[programming/reactive_messaging_pattern/chapter9/consumers/event_driven_consumer|Event-Driven Consumer]]** - ディスパッチされたメッセージを処理するコンシューマーの一形態です。メッセージの到着がパフォーマーを起動します。

- **[[programming/reactive_messaging_pattern/chapter9/consumers/selective_consumer|Selective Consumer]]** - 特定のメッセージのみを選択して処理するパターンです。Message Dispatcherと組み合わせて、専門化されたパフォーマーへの振り分けを実現できます。
