# Messaging Mapper

## パターンの概要

Messaging Mapperは、ドメインオブジェクトとメッセージング基盤の間でデータの変換を行うパターンです。このパターンを適用することで、オブジェクト指向の世界とメッセージングの世界という、根本的に異なる二つのパラダイム間でデータを移動させながら、両者の独立性を保つことができます。

## EIPにおけるMessaging Mapper

### 解決すべき問題

メッセージングを介してアプリケーションを統合する場合、ドメインオブジェクトとメッセージング基盤の間でデータを移動する必要があります。しかし、これら二つの世界は根本的に異なるパラダイムを使用しています。

**オブジェクト指向の世界**では、以下のような概念が当たり前のように使われます。

- オブジェクト参照による他のオブジェクトへの関連付け
- 継承による振る舞いの共有と拡張
- カプセル化されたメソッドによる操作の実行
- 複雑なオブジェクトグラフ構造

一方、**メッセージングの世界**では、状況が大きく異なります。

- メッセージは通常、プリミティブなデータ型や単純な構造体で構成される
- オブジェクト参照は直接表現できない
- 継承関係は通常サポートされていない
- メッセージはシリアライズ可能でなければならない

この根本的なパラダイムの違いにより、ドメインオブジェクトをそのままメッセージとして送信することはできません。何らかの変換処理が必要です。

しかし、この変換ロジックをどこに配置すべきでしょうか。ドメインオブジェクトにメッセージ変換の責務を持たせると、ドメインモデルがメッセージングの詳細に汚染されます。逆に、メッセージング層にドメインの知識を持たせると、密結合が生じます。

### 解決策

メッセージング基盤とドメインオブジェクト間のマッピングロジックを含む、独立した**Messaging Mapper**を作成します。

Messaging Mapperの核心的な特徴は、**両方のレイヤーからの独立性**にあります。ドメインオブジェクトはマッパーの存在を知らず、メッセージング基盤もマッパーの存在を知りません。マッパーは両者の間に位置し、双方向の変換を担当します。

### 双方向の変換

Messaging Mapperは、以下の二つの方向でデータ変換を行います。

**ドメインオブジェクトからメッセージへの変換**では、マッパーはドメインオブジェクト（複数の場合もある）にアクセスし、必要なデータを抽出してメッセージを構築します。このメッセージは送信可能な形式（JSONやXMLなど）にシリアライズされます。

**メッセージからドメインオブジェクトへの変換**では、マッパーは受信したメッセージを解析し、ドメインオブジェクトを新規作成するか、既存のドメインオブジェクトを更新します。

### O/Rマッピングとの類似性

Messaging Mapperは、データベースとの連携で使われるO/Rマッピング（Object-Relational Mapping）と概念的に類似しています。O/Rマッパーがオブジェクトとリレーショナルデータベースのテーブル行の間のインピーダンスミスマッチを解消するように、Messaging Mapperはオブジェクトとメッセージの間のインピーダンスミスマッチを解消します。

## ドメインオブジェクトからメッセージへのマッピング

Messaging Mapperを使用して、ドメインオブジェクト（AggregateやEntityなど）の一部をメッセージにマッピングします。アクターモデルを採用している場合、Aggregate自体がアクターとして実装され、自身の状態のサブセットをEvent Message、Command Message、またはDocument Messageにマッピングすることがあります。

### シンプルなマッピングを心がける

マッピングは可能な限りシンプルに保つべきです。Event Messagesは、「何が起こったか」を伝えるために絶対に必要な値だけを含むべきであり、多くのフィールドや属性を持つべきではありません。

例えば、売り注文が執行されたというイベントを通知する場合、以下のような最小限の情報だけを含めます。

- ポートフォリオID（どのポートフォリオの注文か）
- シンボル（どの銘柄か）
- 数量（何株売却されたか）
- 価格（いくらで売却されたか）

Command Messagesについても同様で、「何をすべきか」を伝えるのに十分なデータのみを含めます。不必要に多くの情報を含めると、メッセージが肥大化し、変更に対する脆弱性が増します。

### アクター自身がマッパーとなるケース

アクターモデルでは、Aggregateアクター自身がMessaging Mapperの役割を担うことがあります。アクターは自身の状態を熟知しているため、必要なデータを抽出してメッセージを構築するのに最適な位置にいます。

この場合、アクターは二つの役割を同時に果たしていることになります。ドメインロジックを実行するエンティティとしての役割と、自身の状態をメッセージに変換するマッパーとしての役割です。この設計は、シンプルなマッピングの場合には効果的ですが、マッピングロジックが複雑になる場合は、専用のマッパーコンポーネントに分離することを検討すべきです。

## 複雑なマッピングを避ける

「マッパー」という言葉を聞くと、複雑なマッピング作業を想像しがちです。例えば、複数のAggregateから情報を収集し、それらを結合して大きなDocument Messageを構築するようなシナリオです。

しかし、このような複雑なマッピングは可能な限り避けるべきです。複雑なマッピングには以下のような問題があります。

**変更の波及**として、複数のAggregateに依存するマッピングは、いずれかのAggregateが変更された場合に影響を受けます。依存関係が増えるほど、変更の影響範囲も広がります。

**パフォーマンスの問題**として、複数のAggregateからデータを収集するには、それぞれのAggregateにアクセスする必要があります。これは、特に分散システムでは顕著なパフォーマンス問題を引き起こす可能性があります。

**テストの困難さ**として、複雑なマッピングロジックは、テストのセットアップも複雑にします。多くのモックやスタブが必要になり、テストの保守コストが増大します。

## CQRSクエリへの対応

しかし、Command Query Responsibility Segregation（CQRS）アーキテクチャにおいてクエリに応答する場合、かなり大きなペイロードを構築する必要があることがあります。読み取りモデル（Read Model）は、複数のAggregateから収集された情報を非正規化した形で保持していることが多く、これをDocument Messageとして返す際には、より洗練されたマッピング処理が必要になります。

### マッパーユーティリティの選択

JVM上で動作するほとんどのマッパーユーティリティは、JavaBeans仕様に基づいて設計されています。これは、オブジェクトがpublicなgetterとsetterを提供することを前提としています。

Scalaのcase classのような不変オブジェクトを使用している場合、この前提は問題になります。case classは通常、publicなsetterを持ちません。この問題を解決するには、フィールドレベルのリフレクションをサポートするマッパーユーティリティを選択する必要があります。

## 単一のStringベースフィールドによる設計

マッパーユーティリティの制約を回避する実用的なアプローチとして、Document MessagesをmessageBodyのような単一のStringベースのフィールドで設計する方法があります。

このアプローチでは、メッセージの実際の内容をJSON（JavaScript Object Notation）やXML（Extensible Markup Language）として文字列にシリアライズし、その文字列をmessageBodyフィールドに格納します。受信側は、このフィールドを適切なパーサーで解析してデータを取り出します。

### JSON シリアライゼーションの利点

JSONを使用したシリアライゼーションには、以下のような利点があります。

**プラットフォーム非依存性**として、JSONは言語やプラットフォームに依存しない標準的なデータ交換フォーマットです。Java、Scala、JavaScript、Python、Goなど、あらゆる言語でJSONパーサーが利用可能です。

**人間可読性**として、JSONはテキストベースのフォーマットであり、デバッグやトラブルシューティングの際に内容を直接確認できます。

**スキーマ柔軟性**として、JSONは動的な構造を持つため、メッセージの構造を柔軟に変更できます。ただし、これは諸刃の剣でもあり、型安全性は犠牲になります。

### シリアライザーとしてのMessaging Mapper

Messaging Mapperは、本質的にはシリアライザーとも考えることができます。オブジェクトをバイト列（または文字列）に変換し、そのバイト列からオブジェクトを復元する処理は、まさにシリアライゼーションとデシリアライゼーションです。

この観点から、メッセージングマッパーを設計する際には、以下の点を考慮することが重要です。

**バージョニング**として、メッセージの構造が時間とともに進化する場合、古いバージョンのメッセージを新しいシステムで読み取れるようにする必要があります。

**後方互換性**として、新しいフィールドの追加や既存フィールドの削除が、既存のコンシューマーに影響を与えないようにする必要があります。

**バリデーション**として、受信したメッセージが期待する構造を持っているかを検証する仕組みが必要です。

## 大きなDocument Messageの消費

大きなDocument Messageを扱う場合、送信側と受信側の間で「契約」を明確にすることが重要です。

**Published Language（公開言語）**として、メッセージを発行するチームは、メッセージの構造とセマンティクスを明確に文書化したPublished Languageを作成します。これは、Format Indicatorパターンで説明されているように、メッセージのバージョン情報やフォーマット情報を含みます。

**Anti-Corruption Layer（腐敗防止層）**として、メッセージを受信するチームは、外部のメッセージ形式から自身のドメインモデルへの変換を行うAnti-Corruption Layerを設計します。これは、Message Translatorパターンとして知られる手法で、外部の概念が自身のドメインモデルを「汚染」することを防ぎます。

この二つのアプローチを組み合わせることで、異なるBounded Context間でのメッセージ交換において、各Context の独立性を維持しながら、効果的な統合を実現できます。

## 関連パターン

- **[[programming/reactive_messaging_pattern/chapter9/gateways/messaging_gateway|Messaging Gateway]]** - Messaging Gatewayがメッセージングの「操作」をカプセル化するのに対し、Messaging Mapperはメッセージと ドメインオブジェクト間の「データ変換」を担当します。通常、Messaging Gateway内部でMessaging Mapperが使用されます。

- **Message Translator** - 異なるシステム間でメッセージ形式を変換するパターンです。Messaging Mapperが内部のドメインオブジェクトとメッセージの変換を担当するのに対し、Message Translatorは異なる外部システム間のメッセージ形式の変換に焦点を当てます。

- **Canonical Data Model** - 複数のシステム間で共通のデータモデルを使用することで、マッピングの複雑さを軽減するパターンです。各システムは自身のデータ形式と正規モデル間の変換だけを実装すればよくなります。

- **Command Message** - アクションの実行を要求するメッセージです。Messaging Mapperは、ドメインの意図をCommand Messageに変換する際に使用されます。

- **Document Message** - データの塊を伝達するメッセージです。複雑なドメインオブジェクトをDocument Messageに変換する際に、Messaging Mapperの役割が重要になります。

- **Aggregator** - 複数のメッセージを1つに集約するパターンです。集約されたメッセージからドメインオブジェクトを構築する際に、Messaging Mapperが使用されることがあります。
